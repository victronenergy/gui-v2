1 Status and scope
==================

1.A This document is step 17.A of PLAN-GUIPLUGINS-BRANDING.txt (the plan). It is a review document, not code. The "role table" in the title is the color table, section 5. Step 17.B takes NOTIFY / CONSTANT from the key categories (4.J). Step 17.D implements the formulas and checks the differences in its visual regression captures against section 8.
1.B Numbering follows the plan (plan 1.A). "Plan 7.L.5" cites the plan; a bare number cites this document.
1.C Every value comes from a script that uses the arithmetic in 2.F (plan 7.L.12), run against themes/color/ColorDesign.json, Dark.json and Light.json in the current gui-v2 tree. The C++ implementation (plan step 17.D) gives the same value for every key in both schemes. "today" is the resolved JSON value. "Victron" is the formula output for Victron's branding colors. diff is the largest difference in any channel, alpha included: 0 to 255. Contrast ratios are WCAG 2 (plan 7.M.1).
1.D 180 keys: every key in the three files. Categories (section 4): branding 9, alias 35, gray 48, blended 26, text on fill 5, data 15, exception 9, palette 33.
1.E Victron result against today: Dark 128 keys exact, 46 with a diff of 4 or less, 6 with a larger diff. Light 87 exact, 64 with a diff of 4 or less, 29 with a larger diff. Every larger shift is in section 8, with its cause.
1.F Minimum contrast: 3.0:1 for white text on a colored fill and for secondary text (plan 19.D, decided). Light button_down: dim(brand) (plan 19.E, decided). 6.A and 6.B list what moves under the alternatives.


2 Basic color operations
========================

2.A mix(a, b, t) = a * (1 - t) + b * t per channel, rounded half up, alpha 255.
2.B blend_onto(color, n, background) = mix(background, color, n / 255): color at alpha n (0 to 255), blended onto background. Plan 7.L.2.
2.C These blend a color onto the scheme's background_primary (plan 7.L.3): dim(x) = blend_onto(x, 179, background_primary), darkish(x) = blend_onto(x, 121, background_primary) (plan 7.L.8), dark(x) = blend_onto(x, 77, background_primary).
2.D font_over_background(n) = blend_onto(font_primary, n, background_primary): a gray between the scheme's background and font. n is a constant for each key: an alpha chosen once to match today's color, by projecting today's value onto the line from today's background to today's font (Dark #000000 to #FFFFFF, Light #FFFFFF to #272622). It is fixed in this table and in Dark.json and Light.json. It is not an OEM property (plan 7.F.2).
2.E text_color_on(f1, f2, ...) = white if white has at least the minimum contrast for white text (3.0:1) against every listed fill, else the darker font_primary (plan 7.M.2). The darker font_primary is the darker of the two schemes' resolved font_primary: #262626 for Victron.
2.F The mixes use integers and round each 8-bit channel half up, so a mix that lands exactly on .5 always rounds up. Example: the plan 16.D Dark branding colors with light_mode_background_factor 0.3 give a Light font_secondary of 14 steps of 5%, a 70% mix. Green channel: 149 * 0.30 + 24 * 0.70 = 61.5, which rounds half up to 62 (#3E3E3C). In double precision, 0.05 * 14 is 0.7000000000000001, the channel comes out just under 61.5, and the result is #3E3D3C. Integer form for a fraction t = p / q: (a * (q - p) * 2 + b * p * 2 + q) // (2 * q). The HSL operations (the light mode background formula, plan 7.J.5 and 7.J.11) use double precision, in the same order as the C++ code, which is built without fused multiply-add, so the script and the C++ code give the same result (plan 7.L.12.b, 7.L.12.c).

3.B Light, derived
------------------

Plan 7.J:

3.B.1 background_primary #FFFFFF: the light mode background formula (plan 7.J.5) with Victron's light_mode_background_factor 1.12 (plan 7.J.10). Black is the end point of the soft clamp (plan 7.J.11), so it lands exactly on white.
3.B.2 font_primary #262626: #000000, then 15% toward #FFFFFF (38.25 rounds to 38). Plan 7.J.7. 15.13:1 on white.
3.B.3 background_secondary #F7F7F7: the same formula on #141414 (plan 7.J.6). HSL lightness 20/255 gives 0.5 + 1.12 x (0.5 - 20/255) = 0.9722. That is above 0.94, where the soft clamp starts, so the soft clamp pulls it to 0.9678, which is 246.80 of 255 and rounds to 247. Today's #FAF9F5 differs by at most 3 in any channel.
3.B.4 page #E5E5E5: 12% from #FFFFFF toward #262626 (228.96, so 229). Plan 7.E said "about #E5E5E4".
3.B.5 font_secondary #807F7C: gray5 #969591 is 2.38:1 on the page and 2.80:1 on background_secondary, under 3.0:1, so it steps 5% at a time toward #262626. Four steps pass: 3.18:1 on the page, 3.74:1 on background_secondary. Plan 7.J.8.

3.C At a minimum secondary text contrast of 4.5:1, light font_secondary would be #646361 (9 steps), which differs from today's gray4 #64635F by at most 2 in any channel.
3.D The darker font_primary, used for text on a colored fill when white does not pass, is #262626 in both schemes.


4 Key categories
================

4.A branding: one of the nine branding colors, which a Branding object may set (plan 7.D, 7.E). The Theme getter reads the resolved list of branding values.
4.B alias: in each scheme, an alias of a branding color or of another alias. A key is an alias of a branding color in a scheme only when today's value equals that branding color's value in that scheme. Text and icon keys may be aliases of font branding colors; background keys may be aliases of background branding colors. Some keys are aliases of a different branding color in each scheme (focus_highlight, splash_logo_icon, the boat and brief page backgrounds, levelsPage_gauge_backgroundColor). The table keeps both mappings.
4.C gray: a computed gray, either font_over_background(n) (2.D) or one of the secondary and tertiary text colors (4.D).
4.D Today Dark secondary text is gray5 and tertiary text (units, button icons) is gray4; Light swaps them (secondary gray4, tertiary gray5). Keys that use the secondary text color are font_secondary in Dark and a font_over_background gray in Light. Keys that use the tertiary text color are a font_over_background gray in Dark and font_secondary in Light. Both keep today's ordering in each scheme.
4.E blended: a dim, darkish or dark color (2.C) of a branding or palette color, or a blend_onto with its own alpha. Which of dim, darkish and dark: the one in the key's name (dim*, dark*, darkish*), else the one whose alpha is nearest the alpha that matches the key's Dark value today (the three alphas came from Dark.json, plan 7.L.9). The same one is used in both schemes, except where the table says otherwise. Plan 7.L.5 still applies: dimRed follows the dim formula.
4.F text on fill: text or icons drawn on a saturated color fill (2.E). The formula lists the fills the rule checks; a note names any other fill the key is drawn on.
4.G data: kept as a hex value, never generated (plan 7.G). Stays in the theme files (plan 7.N.4).
4.H exception: translucent or transparent, kept (plan 7.L.11). One decided change: 6.G.
4.I palette: ColorDesign.json, kept (plan 7.G.1), except the three translucent keys, which are exceptions.
4.J For step 17.B: branding, alias, gray, blended and text on fill keys depend on branding and NOTIFY on themeValuesChanged, as does viewGradient_color2 (6.G). Data, exception and palette keys do not depend on branding.
